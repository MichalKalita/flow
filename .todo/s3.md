# Storage destinations and S3-compatible object storage

## Requested outcome

Support S3-compatible storage beyond AWS. Generate write URLs, list objects, generate signed read URLs, and return ordinary object URLs where public access is configured.

## Confirmed general archive and backup destinations

Log archives and backups must also support ordinary disks and network storage, not only S3. Provide a common destination contract with adapters for local paths, already mounted remote disks, SMB/CIFS shares, NFS, SFTP, FTP/FTPS, WebDAV over HTTP(S), and S3-compatible object storage. This is a practical standard-protocol family, not an S3-only product. Keep the interface extensible for other standard storage protocols and verify compatibility per adapter.

The same destination abstraction provides bounded write/read/list/delete, completion verification, and recovery capabilities. Connector-specific configuration can differ, but log retention, backup policy, retry/terminal behavior, and the explorer must not become separate engines for each protocol.

A non-expert selects a destination type and supplies only necessary facts such as path/share/server and credentials. The wizard applies tested defaults and checks access/capabilities. Native or bundled adapters should avoid requiring users to run mount commands or configure an external agent for ordinary supported network storage. Already mounted disks remain a convenient option, not the only implementation for shares.

Keep live application SQLite on its existing local storage contract. Export immutable closed log chunks and consistent backup artifacts to destinations; this requirement does not move live databases onto a shared network filesystem.

Use separate host backup/archive namespaces and project application namespaces. Bound transfer buffers, staging, retries, and read caches. Handle disconnects, partial files, naming conflicts, quota pressure, and capability differences explicitly. Prefer tested secure connection defaults and keep credentials in the encrypted settings store. Verify completion/checksums before publishing an artifact; select finalize/rename/manifest techniques according to actual adapter guarantees rather than assuming every protocol has S3 or local-filesystem semantics.

## Current implementation

`Files.put` stores PNG data and file metadata atomically in the application's SQLite database; downloads recheck normal READ permissions. This is local storage, not an S3 connector. External native plugin implementations are not currently supported. See [plugin execution](../runtime/src/engine.rs), [file handling](../runtime/src/media.rs), and [runtime documentation](../runtime/README.md).

## Implementation options and recommendation

1. Presigned direct client transfers. Recommend this for normal uploads/downloads to avoid buffering large objects through the runtime.
2. A permission-checked runtime proxy for access requiring immediate per-request authorization or server-side processing. Apply strict byte/time limits.
3. Durable background copy/delete/upload jobs through the common external-effect mechanism for application-driven work.

Configuration needs endpoint, region/signing settings, bucket, addressing mode, credentials, public base URL, and a project-scoped key namespace. Treat compatibility as a tested capability set rather than assuming every provider implements every S3 feature identically. Credentials and namespaces are explicit project configuration; sharing a bucket must not expose another project's objects.

## Proposed upload lifecycle

Authorize an upload intent with a numeric local ID, expected limits/content properties, and an unguessable object key. Return a short-lived signed write URL scoped to that object. Verify completion through a typed plugin operation or verified provider notification. Notifications enter the universal event-input API and use common retries/disposition; they do not run a separate S3 event engine.

Do not mark the application file ready merely because a URL was issued or a client claims upload success. Verify the expected object and applicable size/checksum/content rules. Avoid replacing an existing private object key through a fresh upload intent. Define cleanup for expired intents and abandoned objects.

For reads, check current project permissions before signing a URL. A presigned URL is a bearer capability and can remain usable until expiry; it does not recheck Flow permissions on every storage request. Prefer short TTLs, and use the runtime proxy if immediate revocation is required. Public URLs require an explicit public-object policy, not a fallback for signing failure. See [S3 presigned URL behavior](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html).

Listing must be bounded and restricted to the configured namespace; raw bucket enumeration must not bypass application metadata/permissions. Object keys are connector identifiers, not branded Flow entity IDs. Object writes and SQLite writes cannot be represented as one rollback-capable transaction; use intents, pending states, and reconciliation.

## Confirmed server-log archival use case

The server exports old operational-log segments through host-level destination configuration, including S3-compatible storage and ordinary disk/network protocols. All operational logs are server-owned, with project identity used for filtering; do not create separate project archival destinations or budgets. See [server logs](runtime%20logs.md).

Reuse the connector implementation with separate server credentials, bucket/key namespace, and protected administrative configuration. This host capability does not implicitly share application object stores or grant projects access to mixed-server archives. Upload immutable segments with stable keys and verified completion through the common job/failure mechanism. Configure chunk size separately from the total local log target and schedule export as soon as each chunk closes, not only near eviction. Each HA member logs and uploads for itself, using its own stable server-instance object namespace, with readable server name and instance identity recorded in archive metadata. Multiple servers may use the same bucket without mixing or overwriting their archives; renaming or rotating keys must not change archive ownership.

A minimal server archive uploader can be delivered before application upload intents, signing/listing, and multipart features. Local files awaiting export still count toward the local log target. S3-outage behavior and remote retention are tracked in the logging document, not assumed by the generic storage connector. The existing log explorer must query history available only at its configured archive destination, including S3, with the same filters and merge it with all HA members' local results on the request-receiving server. Support bounded destination reads/manifests and explicit deployment-wide read authority without broadening each member's upload ownership.

The common destination infrastructure supports configurable local/network/S3 [backup storage and restoration](backups.md), using a separately configured backup namespace, retention, verification, and recovery contract. Logs are not business backups.

## Dependencies and verification

Verify adapter capability matrices for local disk, mounted shares, SMB/NFS, SFTP, FTP/FTPS, WebDAV, and S3. Include disconnected destinations, incomplete writes, archive-only reads with the common filters, integrity verification, and actual backup restoration. The requested standard-protocol support is not complete merely because one S3 adapter works.


Depends on [secrets](variables-and-secrets.md), [the typed plugin/event and external-effect contract](external-integrations.md), and local migrations for metadata. It can precede email attachment storage, but email must retain a local-storage option and must not require S3 deployment.

Test endpoint/signing variants, expiry, project prefixes, malicious keys, permission loss, upload finalization, duplicate notifications, bounded listing, rollback leaving no falsely ready metadata, external orphan cleanup, restart during delivery, host/project namespace separation, and server-log export recovery. Logs must exclude signed URLs, credentials, request bodies, and plugin arguments.
