# S3-compatible object storage

## Requested outcome

Support S3-compatible storage beyond AWS. Generate write URLs, list objects, generate signed read URLs, and return ordinary object URLs where public access is configured.

## Current implementation

`Files.put` stores PNG data and file metadata atomically in the application's SQLite database; downloads recheck normal READ permissions. This is local storage, not an S3 connector. External native plugin implementations are not currently supported. See [plugin execution](../runtime/src/engine.rs), [file handling](../runtime/src/media.rs), and [runtime documentation](../runtime/README.md).

## Implementation options and recommendation

1. Presigned direct client transfers. Recommend this for normal uploads/downloads to avoid buffering large objects through the runtime.
2. A permission-checked runtime proxy for access requiring immediate per-request authorization or server-side processing. Apply strict byte/time limits.
3. Durable background copy/delete/upload jobs through the common external-effect mechanism for application-driven work.

Configuration needs endpoint, region/signing settings, bucket, addressing mode, credentials, public base URL, and a project-scoped key namespace. Treat compatibility as a tested capability set rather than assuming every provider implements every S3 feature identically. Credentials and namespaces are explicit project configuration; sharing a bucket must not expose another project's objects.

## Proposed upload lifecycle

Authorize an upload intent with a numeric local ID, expected limits/content properties, and an unguessable object key. Return a short-lived signed write URL scoped to that object. Verify completion through a typed plugin operation or verified provider notification. Notifications enter the universal event-input API and use common retries/disposition; they do not run a separate S3 event engine.

Do not mark the application file ready merely because a URL was issued or a client claims upload success. Verify the expected object and applicable size/checksum/content rules. Avoid replacing an existing private object key through a fresh upload intent. Define cleanup for expired intents and abandoned objects.

For reads, check current project permissions before signing a URL. A presigned URL is a bearer capability and can remain usable until expiry; it does not recheck Flow permissions on every storage request. Prefer short TTLs, and use the runtime proxy if immediate revocation is required. Public URLs require an explicit public-object policy, not a fallback for signing failure. See [S3 presigned URL behavior](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html).

Listing must be bounded and restricted to the configured namespace; raw bucket enumeration must not bypass application metadata/permissions. Object keys are connector identifiers, not branded Flow entity IDs. Object writes and SQLite writes cannot be represented as one rollback-capable transaction; use intents, pending states, and reconciliation.

## Confirmed server-log archival use case

The server must optionally export old operational-log segments to S3-compatible storage through host-level configuration. All operational logs are server-owned, with project identity used for filtering; do not create separate project archival destinations or budgets. See [server logs](runtime%20logs.md).

Reuse the connector implementation with separate server credentials, bucket/key namespace, and protected administrative configuration. This host capability does not implicitly share application object stores or grant projects access to mixed-server archives. Upload immutable segments with stable keys and verified completion through the common job/failure mechanism.

A minimal server archive uploader can be delivered before application upload intents, signing/listing, and multipart features. Local files awaiting export still count toward the local log target. S3-outage behavior and remote retention are tracked in the logging document, not assumed by the generic storage connector.

## Open decisions

- **OBJ-1:** Which S3-compatible providers must be verified initially? Recommend a local test service plus the actual deployment provider, then a published compatibility matrix.
- **OBJ-2:** Are public objects needed? Recommend private by default, public only through explicit project policy.
- **OBJ-3:** Do large uploads require multipart support in the first release? Recommend basic direct uploads first, with a planned multipart milestone if the workload requires it.

## Dependencies and verification

Depends on [secrets](variables-and-secrets.md), [the typed plugin/event and external-effect contract](external-integrations.md), and local migrations for metadata. It can precede email attachment storage, but email must retain a local-storage option and must not require S3 deployment.

Test endpoint/signing variants, expiry, project prefixes, malicious keys, permission loss, upload finalization, duplicate notifications, bounded listing, rollback leaving no falsely ready metadata, external orphan cleanup, restart during delivery, host/project namespace separation, and server-log export recovery. Logs must exclude signed URLs, credentials, request bodies, and plugin arguments.
